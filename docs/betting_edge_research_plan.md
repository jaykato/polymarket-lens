# Bet判断の成績を検証・改善するための設計方針

## 目的

Polymarket Lens を、公開情報を見やすくするビューアから、海外の Polymarket
ユーザーが **どの判断方法に実際の優位性があるかを検証できるツール** へ拡張する。

ここでの優位性は、単純な的中率ではなく、板の実際の約定価格、テイカー手数料、
スリッページ、決済までの保有を含めた期待値と実現損益で評価する。価格が 90% の
ポジションでも、購入コストが 95¢ なら、手数料前の期待値は負になり得る。

この計画は「勝てる」と断言する機能を作るためのものではない。仮説を事前に登録し、
未使用データと仮想運用で検証して、再現する優位性だけを表示するためのものである。

## 現在の土台

現在の `l0-return-calculator` ブランチには、次の部品がすでにある。

- Gamma/CLOB の公開データを SQLite に保存する取得基盤
- YES/NO の価格履歴、マーケットの流動性とスプレッド
- `order_book_snapshots` に保存された注文板を指定金額まで歩く処理
- 指定額に対する平均約定価格、テイカー手数料、Entry cost、決済まで保有した場合の
  算術的リターンを示す UI

次の開発では、これらの「コストを正しく見る」部品の上に、判断確率を作り、その精度を
追跡する層を追加する。

## 成功条件

各判断方法は、同じ時点で入手可能だった情報だけを使い、以下の基準で比較する。

| 指標 | 意味 |
|---|---|
| 的中率 | YES/NO の方向を当てた割合。単独では採用判断に使わない。 |
| Brier score | 予測確率と結果の距離。低いほど確率予測が良い。 |
| Log loss | 極端な誤予測を強く罰する確率予測の評価。低いほど良い。 |
| キャリブレーション | 予測 70% の集合が実際におよそ 70% で解決したか。 |
| 期待値 | 推定確率、実際の買値、手数料から計算した 1 株当たりの見込み損益。 |
| 実現損益 | 保存した仮想ポジションを決済結果で精算した値。 |
| 最大ドローダウン | 仮想資金が最大値からどこまで減ったか。 |

基準となる比較対象は常に「その時点の市場価格をそのまま確率として使う」方法にする。
新しい規則やモデルは、未使用期間でこの基準を上回り、かつコスト控除後の成績が改善した
場合だけ有望候補とする。

## 実装の順序

### A. 解決済み市場の履歴を作る

最初に必要なのは、検証できる正解ラベルである。

1. Gamma API から closed/resolved の市場をページネーション付きで収集する。
2. `condition_id`、イベント ID、カテゴリ、質問文、決済時刻、最終アウトカム、解決状態、
   ルール本文と解決情報を保存する。
3. 各市場について、解決の 30日・7日・24時間・1時間前など、固定された観測時点の価格、
   板、流動性、出来高を保存する。
4. void/invalid/disputed/結果不明の市場は通常の精度評価から分離し、除外理由を残す。

市場の仕様と実際の解決結果は別物である。市場のルール、指定ソース、決済時刻を画面で
確認できるようにし、単に最終価格だけから結果を推測しない。Polymarket の決済は UMA
Optimistic Oracle によって行われるため、決済待ち・異議申立て中の状態も扱う。

### B. 時点固定の評価データセットを作る

未来の情報が混ざると、検証結果は使えない。すべての特徴量には `observed_at_utc` を付け、
その時点以後の価格、解決結果、更新された市場説明を学習・判定に渡さない。

評価行の最小単位は次とする。

| 列 | 内容 |
|---|---|
| `condition_id` / `token_id` | 対象市場と YES/NO トークン |
| `observed_at_utc` | 判断を行った時点（UTC） |
| `horizon` | 決済までの残り時間帯 |
| `market_probability` | その時点の買い気配、売り気配、mid、または実効買値 |
| `entry_cost` | 指定額で板を歩き、手数料を含めた 1 株当たりコスト |
| `liquidity_features` | スプレッド、板の深さ、出来高、板の取得時刻 |
| `prediction_probability` | 評価対象の判断方法が出した YES 確率 |
| `outcome` | 解決済みの YES=1 / NO=0 |

初期段階では、見られる期間の偏りを避けるため、学習期間と評価期間を時系列で分離する。
同一イベント配下の市場が学習側と評価側にまたがらないグループ分割も用意する。

### C. 最初の判断方法を比較する

複雑な AI モデルより先に、解釈できる基準を並べる。

1. **市場価格基準**: mid またはコスト込みの実効買値を確率とする。
2. **分野・期限別補正**: 過去のキャリブレーションから、カテゴリ、価格帯、残存時間、
   流動性帯ごとの一貫した偏りだけを補正する。
3. **関連市場整合性**: 同一イベントの相互排他的選択肢、YES/NO の補完関係、複数の
   閾値市場の単調性を検査する。
4. **外部データモデル**: 対象を一分野に限定して追加する。例として天候なら予報、
   経済なら公表値・コンセンサス、スポーツなら試合前に確定している情報を用いる。

Kronos などの時系列モデルはこの段階の比較対象にする。価格の次の変化を当てる性能と、
最終的な決済結果を当てる性能は別なので、両方を別指標で測る。モデルの出力を採用するのは、
時系列外テストと仮想運用で市場価格基準より改善した後に限る。

### D. コスト込みの仮想運用を作る

判断方法が出した確率 `q` と、板から得た 1 株当たりの Entry cost `c` を使う。

```text
期待値（1株） = q − c
損益分岐確率 = c
```

`c` には、指定額で板を歩いた平均価格とテイカー手数料を含める。決済まで保有する仮定の
初版では、売却コストを引かない。途中売却を扱う版では、将来の bid 側の板、売却時の手数料、
部分約定を必ず含める。

仮想ポジションを作る規則は事前に固定する。例:

- `q - c` が不確実性を上回るときだけ候補にする。
- 市場ごとの最大額、1日あたりの総額、同一イベントへの集中上限を設ける。
- 最低流動性、最大スプレッド、板の最大経過時間を満たさない市場を除く。
- エントリー時点、購入額、根拠となるモデル版、板のスナップショットを保存する。

この機能は実注文を送らない。仮想ポジションの状態（open / resolved / void）と、実際の
決済結果による損益を再現可能に保存する。

### E. 継続的な前向き検証へ移す

過去データだけで規則を選ぶと、偶然に合った規則を見つけやすい。候補を選んだ後は、
規則・閾値・モデルバージョンを固定して、以後の市場で自動的に仮想ポジションを記録する。

週次または月次に、基準市場価格と候補方法を同条件で比較する。件数、損益、キャリブレー
ション、ドローダウン、カテゴリ別のばらつきを表示し、悪化した規則は停止または再検証する。

## データベース拡張案

既存の `markets`、`outcomes`、`price_history`、`order_book_snapshots` は保持する。新規テーブルは
最小限から始める。

| テーブル | 役割 |
|---|---|
| `market_resolutions` | 最終アウトカム、決済状態、決済時刻、ルール・解決情報のスナップショット |
| `evaluation_observations` | ある時点で知り得た市場価格、板、流動性、残存時間、正解ラベル |
| `prediction_runs` | 判断方法・特徴量仕様・学習期間・モデル版・作成時刻 |
| `predictions` | 各観測に対する確率、信頼区間、根拠、採否 |
| `paper_positions` | 仮想エントリー、板・手数料込みコスト、決済損益、状態 |
| `external_observations` | 分野別外部データの取得時刻、出所、原データ、正規化値 |

原データと正規化済みの値を併存させる。外部データは出所・取得時刻・利用許諾を記録し、
後から同じ検証を再実行できるようにする。

## UI 改良方針

後で `html/` に作る UI は、単に「買い／売り」を強調する画面にしない。ユーザーが、
価格、仮説、コスト、根拠、検証結果を一画面で比較できる構成にする。

### 1. マーケット詳細の「判断」パネル

現在の Return calculator の近くに置く。表示項目は次の順が読みやすい。

1. **市場の実効買値**: YES/NO 切替、指定額、平均約定価格、手数料、板の取得時刻。
2. **推定確率**: 市場価格基準と、選択中の検証済み方法を並べる。各値にサンプル数と
   不確実性を付ける。
3. **コスト込み差分**: `推定確率 − Entry cost` を percentage points で示す。
4. **判定根拠**: キャリブレーション補正、関連市場の不整合、外部データとの差などを
   短文で示し、元データへ展開できるようにする。
5. **検証状態**: 「未検証」「過去データのみ」「前向き検証中」「十分な実績あり」を
   明示する。利益を保証するラベルは使わない。

正の差分を緑、負の差分を赤に固定するだけでは不十分である。サンプルが少ない、板が古い、
スプレッドが広い場合は、色を弱めて「判断材料が不足」と表示する。

### 2. 検証ダッシュボード

判断方法ごとに、次の4つを同じ期間・市場群で表示する。

- キャリブレーション曲線: 横軸を予測確率、縦軸を実際の YES 解決率とする。対角線と
  信頼区間、各ビンの件数を表示する。
- コスト込み累積仮想損益: 市場価格基準と各方法を重ね、最大ドローダウンを併記する。
- 分野・期限・流動性別の成績表: 良い区分だけを選んだ後の結果は別表示にし、全体結果と
  混同しない。
- 仮想ポジション一覧: 判断時刻、エントリーコスト、推定確率、理由、現在状態、決済損益、
  モデル版を追跡できるようにする。

### 3. 整合性チェック画面

イベント単位で表示する。候補者市場のような相互排他群では、各選択肢を実効買値で合計し、
100% からの乖離を出す。閾値市場では「$X超え」の確率が「$Y超え」（X > Y）を上回るような
単調性違反を出す。

ここでは表示価格ではなく、実際に各ポジションを取得できる ask と手数料を使う。複数市場の
ルールや決済条件が完全に一致するかは自動断定せず、質問文・ルール・決済時刻を並べて
ユーザーが確認できるようにする。

### 4. UI の実装原則

- デフォルトは `UTC` とし、必要に応じてローカル時刻表示へ切り替える。表示するすべての
  板・予測・外部データに観測時刻を付ける。
- 金額、確率、手数料、スリッページ、サンプル数を同じ桁数と単位で表示する。
- 推定確率と市場価格を視覚的に区別し、どちらがモデル由来かを常に分かるようにする。
- モデル名だけで信用度を示さず、データ期間、評価件数、直近の成績への導線を置く。
- 一覧画面の並び替え候補に `cost-adjusted edge` を追加するのは、前向き検証で有用性を
  確認してからにする。

## 実装時の注意

- 手数料率はカテゴリ名から推測せず、対象マーケットが返す設定を保存して使う。Polymarket の
  テイカー手数料は価格にも依存し、maker は課金されない。
- 取得済み板だけでは経時的な売買戦略の検証に足りない。板の時系列を使う機能に進む前に、
  対象市場と取得頻度を定めて継続収集を始める。
- NO 側の板を YES 側から反転している現在の前提は、NO トークンの実板と照合して検証する。
- 価格履歴の最終点を「ある判断時点の価格」とみなすときは、その点が本当に当時保存された
  ものか、後から取得した履歴なのかを区別する。
- 外部データの取得失敗、遅延、利用条件の変更を成績改善と取り違えない。

## 最初の具体的なマイルストーン

1. `main` に L0 を取り込んだ後、注文板の取得時刻表示とスナップショットの保存方針を確定する。
2. resolved 市場を取得・保存し、結果を検証できる CLI コマンドを追加する。
3. 解決 24時間前の市場価格基準について、キャリブレーション表と Brier score を出す。
4. 同じ市場群で、板・手数料込みの仮想ポジションを精算する。
5. 市場価格基準より良い候補が現れた場合だけ、分野・期限別補正を追加する。
6. 前向き検証を始め、十分な期間の結果を得てから外部データや Kronos を比較する。

この順序なら、AI モデルや外部データに先走らず、既存の価格・板・手数料の基盤から、
実際に成績が改善するかを段階的に確かめられる。
