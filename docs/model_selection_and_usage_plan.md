# Polymarket Lens: モデル選択と利用方法の方針

## 目的

モデルの目的は「市場価格を上回る確率推定または価格経路の情報があるか」を、
コスト込みの仮想運用で検証することである。モデル名や予測精度だけで採用しない。

比較対象は常に、判断時点の Polymarket 市場価格をそのまま確率として使う方法とする。
新しいモデルは、未使用の後続期間でこの基準より良く、かつ板・手数料込みの仮想運用で
改善が続く場合だけ候補にする。

## 既存資産の位置付け

`E:\models` には、Kronos-small と、国内株の短期売買向けに作られた LightGBM の
メタラベルモデル群がある。

| 資産 | Polymarket での使い方 | 直接再利用の可否 |
|---|---|---|
| Kronos-small | 価格経路・変動幅・不確実性の予測候補 | 重みは試験可能。ただし入力を Polymarket 用に作り直す必要がある。 |
| `metalabel*` | 特徴量定義、時系列分割、評価・確率補正の設計参考 | 学習済み重みは使わない。国内株の銘柄・指数・寄り付き特徴量は移植できない。 |
| LightGBM | Polymarket 専用の表形式モデルとして再学習する第一候補 | 新規学習する。 |
| Chronos 系 | Kronos の比較対象となる汎用時系列モデル | Kronos が基準を上回った後に追加する。 |

## 採用モデル

初期実装は **Chronos-2のみ** とする。AmazonがApache 2.0で配布している
`amazon/chronos-2` を、初回の `forecast` 実行時にHugging Faceから利用者のローカル
キャッシュへ取得する。120Mパラメータで、単変量・多変量・共変量と分位点予測を扱える。

導入手順は次の通り。

```powershell
pip install -r requirements-model.txt
python -m polymarket_app forecast TOKEN_ID --steps 24
```

`forecast` の初回実行時にモデルファイルが Hugging Face からローカルキャッシュへ取得される。
`--device cuda` を指定すればGPUを利用する。`--interval-minutes 0`（既定値）は、保存済み価格の
実測間隔から入力間隔を選ぶ。

Kronos-smallは現段階では採用しない。金融OHLCVを前提とするKronosの評価には、より密な
注文板・約定データを継続収集してから取り組む。

## 採用する比較順

モデルを一度に増やさない。次の順序で、各段階の成績を固定してから次へ進む。

1. **市場価格基準**
   - YES の市場価格、最良ask、指定額で板を歩いた実効Entry costを保存する。
   - 決済24時間前、7日前など固定した時点で、Brier score、log loss、キャリブレーション、
     コスト込み仮想損益を出す。

2. **確率補正基準**
   - 過去の解決済み市場を、価格帯・残存時間・流動性帯で分ける。
   - 十分な標本がある区分だけ、Beta平滑化またはロジスティック回帰で市場価格を補正する。
   - 標本が不足する区分では市場価格へ戻す。補正値を作らない。

3. **Polymarket 用 LightGBM**
   - 市場価格、直近の価格変化、変動幅、残存時間、流動性、スプレッド、板の深さ、
     出来高、カテゴリ、イベント内の関係を特徴量候補にする。
   - ラベルは最終YES/NO。各観測時点より後の価格、解決情報、更新済み説明文を渡さない。
   - 最初は市場価格を特徴量に含めた小さいモデルにし、特徴量を一つずつ増やす。

4. **Chronos-2**
   - 一定時間後の価格の10%、50%、90%分位点を予測する。
   - まず価格のみを入力し、その後に流動性・スプレッドなどの過去共変量を加える。
   - 出力をLightGBMの追加特徴量にし、LightGBM単独より改善するか比較する。

## Chronos-2 の利用方法

Chronos-2は固定間隔の系列を入力する。Polymarketの価格履歴は不規則なことがあるため、
保存済みの過去価格だけを用いて、5分・15分・1時間などの固定間隔へ前方補完する。

- 5分、15分、1時間など、固定間隔の観測系列
- 欠測区間は過去の最後の価格だけで前方補完する。未来の値による補間は禁止する
- 同一マーケットについて、入力終了時点と予測対象時点を記録する
- 利用できるようになった時点で、流動性・スプレッド・板深さを過去共変量として加える

最初はCPUで再現可能な出力を確認し、その後にGPUとの一致とレイテンシを測る。

Chronos-2の出力は、次のような特徴量に変換する。

| 特徴量 | 内容 |
|---|---|
| `forecast_return` | 現在価格に対する予測終値の変化率 |
| `forecast_range` | 予測経路の最大値と最小値の差 |
| `forecast_uncertainty` | 複数サンプル予測のばらつき |
| `market_vs_forecast` | 市場価格と予測終値の差 |
| `forecast_direction_agreement` | Chronos-2の方向と直近市場変化が一致するか |

Chronos-2単独の「次の価格が上がる」予測をベット根拠にしない。価格変化を当てても、最終決済結果や
コスト後の損益を改善しないことがあるためである。

## データと評価の必須条件

### 時系列分割

ランダム分割は使わない。古い期間で学習し、後の連続期間で検証するwalk-forward方式を使う。
同一イベントに属する市場は、可能な限り同じ分割側に置く。

```text
学習期間 ─────────┬── 検証期間 ───┬── 最終テスト期間
                  モデル選択          採用判定
```

最終テスト期間の結果は、モデルや閾値を選ぶために使わない。

### 予測の記録

各予測について、少なくとも次をSQLiteへ保存する。

- モデル名、モデルファイルのハッシュ、特徴量バージョン
- 学習期間、評価期間、ハイパーパラメータ
- `observed_at_utc`、対象マーケット、対象トークン、予測時の入力値
- 市場価格、実効Entry cost、予測確率、予測区間、採用・見送り理由
- 最終アウトカム、仮想ポジションの損益

これにより、後からモデル・特徴量・閾値を変えても、過去結果との比較を再現できる。

### 評価指標

| 層 | 指標 |
|---|---|
| 確率の正確さ | Brier score、log loss、キャリブレーション曲線 |
| 順位付け | ROC-AUC、PR-AUC、上位デシルのYES率 |
| 運用 | コスト込み仮想損益、最大ドローダウン、ポジション数、カテゴリ別成績 |
| 実用性 | 推論時間、失敗率、入力欠損率、再現性 |

採用判定には運用指標を必ず含める。的中率やAUCだけが良くても、手数料・スプレッド・
スリッページ後に利益が残らなければ採用しない。

## 実装上の判断

- `polymarket-lens` の標準ライブラリのみという現状の方針を保つため、モデル学習・推論は
  まず別の `research/` または `tools/` 環境で行い、結果をSQLiteへインポートする。
- ランタイムへPyTorchやpandasを追加するのは、モデルが前向き検証を通過してから判断する。
- `E:\models` はモデル資産の正本として扱う。アプリから直接参照せず、採用候補のコピーと
  マニフェストをプロジェクト側へ置く。
- ONNX化は採用後の配布・推論最適化の段階で検討する。モデル選定段階では、正しい時系列評価と
  入力再現性を優先する。

## 採用ゲート

各モデルは、次の条件をすべて満たしたときだけ「検証済み候補」と表示する。

1. 市場価格基準より、後続期間のBrier scoreまたはlog lossが改善している。
2. コスト込み仮想損益が、市場価格基準以上である。
3. 複数の連続した評価期間、または複数カテゴリで極端に崩れていない。
4. 予測確率がキャリブレーションされ、標本数と不確実性が表示できる。
5. モデル・特徴量・入力データの版を再現できる。

現時点では、解決済み市場の標本数と中間確率帯の件数が不足している。まず収集期間を伸ばし、
市場価格基準と単純補正の前向き検証を安定させてから、Polymarket用LightGBMとKronosを比較する。
